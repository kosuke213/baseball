# 第9段階への接続仕様

## そのまま使うAPI

- `fullgame.engine.Team / fictional_team / Game`：名簿、1窓の`step`、全試合の`run`、交代。
- `fullgame.model.GameModel`：第7段階の確率＋2023〜2024年の成績付き経路。`predict_pa / predict_step / resolve_outcome / sample / support_report`。
- `fullgame.rules.GameRules / Play / Credit / apply_play / next_half`：確率から分離した設定・裁定・状態更新。
- `fullgame.history.GameJournal / replay_rows`、`storage.replay_game`：保存した決定だけから状態・個人成績を再構築。更新後の確率モデルは不要。
- `fullgame.storage.HistoryStore`：試合・日付・球団・出場選手・個人成績・イベントの検索保存。
- `fullgame.league.schedule / validate_schedule / Standings / league_gate`：12球団各143試合の日程と限定した順位集計。試合運営そのものの完成を意味しない。

## 試合・履歴の単位

1窓の抽選は、打席完了までの途中プレーを含みます。旧 `PitchOutcomeModel` の1球へ変換せず、別の実験モードとして起動してください。途中盗塁を別途抽選すると二重計上になります。

通常APIは履歴を記録します。`record=False` はヘッドレス検証用で、`HistoryStore.save` は履歴なしの結果を歴史として保存しません。保存時は全履歴を再生し、最終状態・イニング得点・全個人成績まで一致することを確認します。

試合IDは球団名簿・日付・シード・設定・モデル版・ルール版から決まります。同じIDで異なる履歴は拒否します。SQLiteの`games / appearances / journal_events`は更新・削除をトリガーで拒否。同一試合の同一内容の再保存は重複追加しません。試合IDとモデル版には名簿・設定とモデル指紋を含み、後からモデルを更新しても既存結果を抽選し直しません。

移行が必要な場合は新しいスキーマ版・DBへ明示的に移し、元DBと元のジャーナルを保持してください。ハッシュ連鎖は破損検知であり、外部への電子署名や改ざん防止サービスではありません。

## 第9段階で先に直すこと

1. `runner_only_end` が通常回の終了・サヨナラ等を兼ねる問題を、終了種別とゲーム状況を持つ定義へ分解する。確率だけを都合よく0へして完走率を作らず、学習母集団・分母・モデル版の変更と再評価を行う。
2. 未観測の二重走塁死等に推測で個人IDを割り当てない。必要な原本・規則を解析し、十分な経路が得られない場合は停止を保つ。
3. サヨナラの得点とアウト、公式安打価値のタッチ順、窓内交代を復元し、曖昧なケースを経験的終点だけで公式判定したと称しない。
4. 自責点・救援裁量・資格等を実装する場合、実験上の集計と公式記録の対応可否を項目別に検証する。
5. 架空能力と確率を結び付ける前に、現在のリーグ平均フォールバックを基準に分布と偏りを確認。MLBからNPBへの移行は別の校正・独立評価とする。

## リーグ試験の開始条件

少なくとも1,000試合で停止0、個人成績整合性エラー0、優先記録の未確定0を条件とします。条件を満たさなければ858試合の実行は見送ります。条件を満たして開始しても、途中で停止したらその時点の失敗を残して未達とし、未実施試合を0点や引き分けで埋めません。

順位表は勝率（引き分け除外）、同率時は勝数、なお同率は同順位という実験規則です。球団IDは表示順のみ。NPBの公式順位決定規則、交流戦・カード連戦・移動距離・休日・故障・疲労・成長・契約・経営は未実装です。

## 評価と追加データ

2025年は既知の参考期間です。新年度の予測や校正改善を主張するには、利用条件を確認した未使用期間が必要です。取得済みのNP・ラインアップ・原本のプレー記述をまず解析し、追加取得は不足が確定した情報へ絞ります。原本で裁定済みの得点を使うモデルと、詳細な時間順序を自力で判定できるルールエンジンを区別してください。

12球団の長期世界に進める際は、名簿の版・開催日・試合ID・モデル版・ルール版を継承します。将来成績をあらかじめ固定する機能は追加せず、試合ごとの確率抽選で履歴を積み上げます。
