# 第3・第4段階：共通DBへの整理と収集範囲の拡張

**共通DBを構築し、2023〜2025年のレギュラーシーズン全試合へ収集を拡張しました。** [全件DBとCSVをダウンロード（約44 MB）](https://raw.githubusercontent.com/kosuke213/baseball/codex/data-warehouse/data_sources/warehouse/database_bundle.zip) / [Windowsでの開き方](../../data_sources/warehouse/README.md) / [必須の出典表示](../../data_sources/warehouse/ATTRIBUTIONS.md)

## 第3段階：別々の資料を結べる形へ

試合・球団年度・球場・人物・外部ID・プレーを、型と外部キーを持つSQLiteの表に整理しました。取得元を表す接頭辞を付け、同じ数字や文字列のIDが別サイトで衝突しないようにしています。

| 対象 | 共通キーと保存内容 |
|---|---|
| 人物 | ChadwickのUUID。Retrosheet・MLBAM・NPB・BBRef等は別の識別子表へ。氏名では自動結合しない |
| 球団 | Retrosheetコード＋年度。リーグと所属年度を保持し、移転・改名を推測で同一球団にしない |
| 球場 | Retrosheet球場コード。掲載時点の名称と資料不足を区別。球場内気象や現代の名称を過去へ補わない |
| 試合 | ホーム側コード・開始日・同日試合番号。再開後のイベント日も別に保持 |
| プレー | 試合ID＋プレー順。得点・アウト・走者・投打者・イベント原記号などを型付き列へ |
| 気象 | 観測所＋UTC時刻＋観測項目。JST・単位・元の文字列・セル属性・値の種類も保存 |
| 日本の候補情報 | 元資料内の識別子と注記。外部人物IDがないため、独立した二次資料として保存 |

各行から原本ID・原行番号・URL・SHA256へ戻れます。プレーの177原列は年別ZIPにそのまま残っています。共通表へ取り出していない列も、将来必要になった際に `source-row` コマンドで再確認・再抽出できます。大量の原本はGit外の共通ストアにあり、配布ZIPには型付きDBと取得・再構築の根拠を含めています。

人物5,449件、外部ID対応21,989件、球団年度90件を保存しました。3年間には31種類の球団コードが現れます。年度ごとは30球団で、過去と現在のコードを名前だけでまとめていません。球場は実使用39コード、参照表と合わせて266コードを保持しました。

東京の気象は第2段階の24時間分を引き継ぎ、16項目×24時刻の384観測項目へ整理しました。日本の候補ボード18件も引き継ぎました。気象の日数や日本の候補数を今回増やしたとは扱いません。

33原本、計92,164,066バイトを保存・再検査しました。2023・2025年の追加年別ZIPと球場表を取得し、既存の2024年・人物参照表等を再利用しています。オールスターやポストシーズン134試合群・10,567行はレギュラーシーズン表の対象外として件数・理由を明示し、原本には残しました。正規化した `plays` は上表の全行です。

## 全件検査で分かったこと

7,289試合について、イニング別スコア、得点・アウトの推移と最終値、プレー順、攻撃チーム、打数・安打・本塁打・四球・三振を照合しました。最終版では不一致0件、SQLiteの整合性・外部キー検査も正常です。打者・投手2,067 IDは全て一意に対応しました。

標本にはなかった、**3アウト後にNPの選手交代行が残る例が1行**ありました。また、**延長の先頭NP行の後に自動走者が二塁へ配置される境界が8件**ありました。原本を改変せず、2023〜2025年のMLBレギュラーシーズン、10回以降、無得点・アウトなしの先頭NP行から二塁への配置という条件に限定して認識しています。[MLBの公式説明](https://www.mlb.com/glossary/rules/designated-runner)も確認し、根拠URL・確認日・資料の指紋をDBに残しました。走者の資格まで独立して再判定したものではありません。

検査で問題が出た試合は `game_checks` と `quarantine.csv` に残し、原行を保持したまま `analysis_plays` から除外できます。最終版は全7,289試合が通過し、隔離対象0件です。NP行を含むため、570,548行は投球数・打席数ではありません。

残っている資料不足は次のとおりです。

- 球場表は2022年最終更新の資料でした。BIR01・BST01・MEX02・SAC01・SEO01・TAM02の6コードは参照情報がなく、名称や座標を創作せず `unresolved` として保持。
- 試合ログ中の審判ID `jascs901` 1件が人物参照表と未対応。打者・投手の対応とは分けて報告。
- 日本の候補表に外部人物ID・行単位の出典・verified列がない点は継続。氏名やスカウティング評価を根拠に公式値へ統合しない。
- NPB公式・Statcast等の本体は利用条件の未解決があるため引き続き保留。ライセンスの異なる二次配布から迂回取得していない。

照合はRetrosheet内の別形式同士の整合性確認で、独立した原スコアカードとの突き合わせではありません。特定の年代・リーグでの全件一致を、他の年代・リーグの完全性の根拠にしていません。

## 再開・更新・履歴

取得状況をファイルごとに記録し、途中停止後も成功原本から再開します。同じ入力・変換コード・Python/SQLiteの版で再実行した場合は、指紋を再検査して既存の完成版を再利用します。取得・変換・出力の失敗時は、それまでの現行DBを置き換えません。同時実行もSQLiteのプロセスロックで防ぎます。

原本・条件・変換コードの版が変わった場合は、別のスナップショットとして保存します。固定lockと旧DBをその場で更新しません。更新の検知結果は [update_check.json](../../data_sources/warehouse/update_check.json) に記録します。取得条件が変わった場合は、利用条件の再確認が必要な候補と分かるようにしています。

GitHub Actionsの手動・週次実行用設定も作成しました。**現時点では作業ブランチ上の設定で、定期収集を常時稼働させてはいません。** 既定ブランチへ反映・有効化した後に、固定計画の取得・検査と更新候補の確認を実行し、DBをActionsの成果物として保存できます。新年度や未確認の提供元を無制限に追加する設定ではありません。
