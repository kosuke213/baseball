## 1. 実装したフルゲームエンジン

`baseball_simulation_lab.fullgame` を追加しました。第7段階の確率モデル、選手IDの型、基本ルールを優先して再利用します。旧一球モデルのモード・UI・保存記録は保持し、新しい打席窓モデルを一球として渡す変更はしていません。

2球団の9人の打順、現在投手、塁上の選手ID、回・表裏、アウト、得点を持ち、1窓ずつの `step()` と最後までの `run()` を提供します。安打・四死球・三振・基本走塁・併殺等の結果を処理し、3アウトで交代、ホームがリードしていれば裏9回を省略します。

延長上限、同点での引き分け許可、二塁自動走者を置く回は `GameRules` で変更できます。今回の主検証は9回制・最大12回・引き分けあり・自動走者なしです。特定リーグの規則が普遍的だとはしていません。上限で同点かつ引き分け禁止の場合は停止し、勝者を作りません。

代打・代走・投手交代はカウント開始前の基本処理に対応。代走・投手交代後も既存走者の責任投手を保持します。主検証では7回以降の最初の機会に救援1人を使う固定方針で、実測した疲労モデルではありません。

打席窓は途中の盗塁・暴投等を含む場合があります。窓全体と別の盗塁を重ねて抽選しません。途中の走塁死で第3アウトとなれば、打席数を加えず、次回も同じ打者の打順を維持します。

## 2. ルールと公式記録の対応範囲

| 項目 | 対応状況 |
|---|---|
| 先攻・後攻、打順、走者ID、攻守交代 | 対応。走者の重複・理由のない消失・得点と移動の不一致を拒否 |
| 9回裏省略、延長・引き分け・自動走者設定 | 対応。自動走者配置を打席や安打として数えない |
| 通常のサヨナラ、本塁打の全得点 | 対応。非本塁打は勝利点までで打ち切る |
| サヨナラ安打の価値 | 勝利点に必要な塁数へ短縮する限定対応。タッチ順が確定できない場合は停止 |
| サヨナラ犠飛 | 捕球による打者1人のアウトが得点より先と証明できる通常例に対応 |
| 途中走塁、併殺、原本で確認した特殊進塁 | 選手IDを保持して処理。詳細な時刻・裁定まで自力で復元したとはしない |
| 交代 | カウント開始前の代打・代走・投手交代。途中カウントの責任・全資格規定は未対応 |
| 打席・打数・安打・長打・四死球・三振・得点 | イベントから集計してチーム・投手側と照合 |
| 打点 | 原本の得点者別打点を使用。仮定の進塁等で未確定ならnull |
| 投球回・被安打・失点 | 投球回は整数アウト数。失点は責任投手へ帰属。複雑な置換で未確定ならnull |
| 勝敗投手 | 決勝走者、最後に取り戻されなかったリード、先発5回条件等の限定対応。救援の裁量判定は要確認 |
| 自責点・セーブ・ホールド | 未実装。0で補わずnull |
| 全公式記録 | **未完成**。`full_official_record=false` を維持 |

定義の確認にはMLB Official Baseball Rules 2025の5.08、9.02、9.04〜9.06、9.08(d)、9.16(g)、9.17を参照しました。PDFの版・URL・指紋は[出典](../../data_sources/stage8/ATTRIBUTIONS.md)に保存しています。NPBの全規則へ適合したとは称していません。

### 第7段階の「8停止」をどう扱ったか

- **2件は仮定を明示すれば処理可能**：二死三塁の野選です。三塁走者をアウト、打者を一塁へ置いて残塁とする限定的な仮定を追加しました。**実測された新経路とは扱いません。** 原本限定モードでは、この仮定を使いません。

## 6. 同じシードからの再現と、歴史の保存

通常のAPIとCLIは完全なイベント履歴を記録します。試合ID、開催日、球団ID、出場選手、最終スコア、各回得点、個人成績、主要イベント、モデル版・ルール版・シードを保存します。

`GameJournal` は元の `Journal` の仕組みを拡張し、初期状態・名簿・設定・決定した各プレーと前後状態の指紋を連鎖させます。`HistoryStore.save` は全履歴を再生して、**最終状態だけでなく個人成績まで一致**することを確かめてから保存します。更新後モデルを呼んで再抽選しません。

SQLiteは次の検索単位を持ちます。

| テーブル | 内容 |
|---|---|
| `games` | 試合ID、日付、球団、結果、スコア、モデル・ルール版、シード、結果JSONと指紋 |
| `appearances` | 試合・選手・球団・打撃／投球区分、主要件数と全成績JSON |
| `journal_events` | 試合ごとの順序付きの再生可能イベント |
| `metadata` | スキーマ版 `fullgame-history-1` |

同一試合・同一内容の再保存は重複登録せず、同じIDで違う内容は拒否。既存の試合・選手成績・イベントに対するUPDATE／DELETEも拒否します。移行は元DBを保持したまま新スキーマへ行う設計です。ハッシュは破損検知で、外部署名サービスではありません。

大規模な試行はヘッドレス検証用で、全1万試合を公式の歴史として保存したとはしていません。全試行のサマリーと全155停止の状況を保存し、主検証10試合・対照2試合は個人成績を含む完全な履歴を保存・再生しました。`record=False` の結果は履歴保存APIが拒否します。実際のリーグ運用では通常の履歴記録モードを使う必要があります。

配布ZIPを独立したフォルダーで展開し、`python -S`（追加ライブラリを読み込まない設定）で例を実行しました。既定シード8000は**7対14でホーム勝利、裏9回省略**。同じシードの再実行は同じ試合ID・スコア・個人成績になりました。モデルのファイルを隠した状態でも、保存した主10試合・対照2試合・利用例1試合の再生検証が成功しました。[検証記録](verification.json)

## 10. 起動・再生・再構築

ダウンロードZIPではPython 3.11以上を用意し、展開先で実行できます。

```powershell
py -3 example.py --model-dir . --db my_history.sqlite3 --journal my_game.jsonl
```

リポジトリのルートでは以下を使います。`simulate` の既定は原本限定モードです。主検証と同じ仮定を許可するなら `--allow-assumptions` を明示します。

```bash
.venv/bin/python -m baseball_simulation_lab.fullgame simulate --seed 8000 --db data/fullgame/history.sqlite3
.venv/bin/python -m baseball_simulation_lab.fullgame replay --db data/fullgame/history.sqlite3 --game-id YOUR_GAME_ID
.venv/bin/python -m baseball_simulation_lab.fullgame build
.venv/bin/python -m pytest -q
```

`build` は第5〜7段階の固定入力が必要です。対応する原本の復元場所と別保存先の指定は[実行README](../../data_sources/stage8/README.md)を参照してください。新規のプレーデータ取得は0件です。

## 11. 残る重大な制約・未達事項

1. 155試合が止まり、無人でシーズンを必ず完走できない。通常のサヨナラ犠飛以外のアウト順・タッチ順、通常回と試合打ち切りを混同する終了ラベルの整理が必要。
2. 完了試合でも54試合の打点が未確定。自責点・セーブ・ホールド、複数救援の裁量、登録資格・最低対戦打者などは未完成。
3. 原本の途中交代・NP・ラインアップ、複数アウトの残塁2例は解析未対応。原本自体の情報不足と断定しない。
4. 架空能力、疲労、守備、球場、成長・故障、ドラフト、契約・経営・ファン参加は未接続。今回の選手IDは成績を区別するためで、全員に実在成績を自動付与していない。
5. NPBへ校正しておらず、独立した予測評価期間もない。858試合の実行と本番リーグ運営は未達。
